# ALIGNMENT localization

The campaign supports English (`en`), French (`fr`), Spanish (`es`), Portuguese
(`pt`, Brazilian usage), Arabic (`ar`, Modern Standard Arabic), German (`de`),
and Italian (`it`). English is the first-visit default regardless of browser
language. The native navbar selector persists an explicit choice in
`localStorage` under `alignment-language`.

## Files and editing

- `locales/*.json`: seven complete dictionaries with 136 matching keys each.
- `assets/i18n-catalog.js`: generated browser dictionary bundle; do not edit.
- `assets/i18n.js`: in-place text/attribute updates, preference handling,
  language/direction, feedback and fallback.
- `scripts/build-locales.cjs`: dependency-free bundle generator and key checks.
- `index.html`: English fallback markup, stable binding keys, selector, and
  logical/RTL styles. Existing campaign JavaScript still owns media and FAQs.
- `qa/i18n.cjs`: automated language, layout and interaction audit.

After changing translations, run:

```sh
node scripts/build-locales.cjs
```

The generator rejects mismatched keys, blank/non-string entries, missing
interpolation tokens and HTML references to missing keys. Keep English JSON and
English fallback markup synchronized when changing source copy. No external
translation API, exposed credential, runtime library, or production build service
is involved. The generated bundle is deliberately small enough to load all
languages together, making the first and subsequent switches immediate and
allowing translation even when opening the HTML file directly. The production
site remains static.

`data-i18n-text` binds an element's direct, nonempty text nodes in key order.
Children such as italic emphasis, line breaks, product links, the copyright
year, and hidden icons remain intact. Where an element has two direct text
nodes around a child, its attribute lists two keys separated by a space. Do not
add a direct text node without adding its binding. Attribute bindings use
`data-i18n-alt`, `data-i18n-aria-label`, `data-i18n-content`, etc. Dictionaries
contain plain text; the runtime does not insert translated HTML.

For example, chapter keys use `chapters.chapterOne.title` and
`chapters.chapterOne.description`. Shared CTAs use `buttons.exploreCombo` and
`buttons.getCombo`. FAQ answers retain their original real Shopify link, with
translated text before, inside, and after that link. A separate access-link key
supports the grammatical case required by German.

## Behavior and scope

Switching updates all active campaign text, accessible names/descriptions,
image descriptions, video fallback/error text, document title, description and
Open Graph title/description. It sets the HTML language and `dir="rtl"` for
Arabic; other languages use `ltr`. The layout uses logical alignment and borders;
brand lockups and numbering retain their original order. Images and video are
not mirrored, replaced, or translated. Text embedded in media is unchanged.
Browser-provided media controls use the browser's own UI language.

The switcher changes text nodes and attributes, preserving video playback,
expanded FAQs, menu state, focus, destinations and scroll position. If a shorter
translation reduces the document below the old scroll coordinate, normal browser
scroll bounds apply. Rapid switches apply synchronously; final scroll restoration
runs on the next animation frame. A polite status announces successful switches.

The dictionaries load as one local script. If that bundle or a requested
translation is missing/incomplete, the existing English markup remains usable,
the selector returns to English, and a visible message explains the fallback.
An unsuccessful language load does not overwrite the saved preference. Storage
failures are caught; switching still works for the current visit. Unsupported
saved language values use English. With JavaScript disabled, English remains
available and the language control is disabled.

Shopify destinations and security attributes are unchanged. No language
parameters are appended, and no claim is made that Shopify supports these
languages. Product contents, prices, delivery and access remain unverified;
the translated FAQs retain the same references to the official product page.
A stale mobile journey anchor now targets the existing `#offer` journey content.

## Editorial review required before international advertising

These are complete authored translations, not certified or native-speaker
approved translations. Arrange native editorial and Christian theological review
for all six non-English languages before using them in paid campaigns. Review
especially alignment/divine positioning, purpose versus destiny, provision,
spiritual authority, repentance, covenant relationships, the Toronto account,
and the author's biography. Establish ministry-approved terminology, regional
Portuguese/Spanish/French preferences and approved localized product-title usage.

ALIGNMENT, Bible Davids, Bible Davids Ministries, Shopify and the official
English product subtitle remain proper names where appropriate. The title of
the ministry office is localized in the biography; the person's name is retained.
No claims of translated books, dubbed video, translated checkout, or localized
fulfillment have been added. Hidden no-JavaScript explanatory copy and commented
out historical sections remain English; neither is shown in the translated,
JavaScript-enabled campaign. There are no live forms or validation messages.

## SEO and future localized routes

This is one URL with client-side language state. No misleading `hreflang` or
unverified canonical URL is added. Default HTML and social scraper previews are
English; updating metadata in the browser does not guarantee localized search
indexing or ad/social previews. Before an international SEO rollout, plan
stable language-specific URLs, server-rendered/pre-rendered locale content and
previews, correct self/alternate canonicals and `hreflang`, sitemap entries,
and locale-specific paid-ad URLs. The stable dictionary keys and
`window.AlignmentI18n.setLanguage(code)` entry point can support a future route
adapter. No speculative routing or query handling has been added.

## Local preview and QA

From the project directory:

```sh
python3 -m http.server 8000 --bind 127.0.0.1
```

Open `http://127.0.0.1:8000`. No build step is needed for preview. A fresh browser
profile starts in English. Clear `alignment-language` in localStorage to reset
a saved choice.

The QA script uses temporary development dependencies described in `qa/README.md`:

```sh
NODE_PATH=/tmp/alignment-qa-tools/node_modules QA_OUTPUT=/tmp/alignment-i18n node qa/i18n.cjs
QA_BROWSER=webkit PLAYWRIGHT_BROWSERS_PATH=/tmp/alignment-browser-tools NODE_PATH=/tmp/alignment-qa-tools/node_modules QA_OUTPUT=/tmp/alignment-i18n-webkit node qa/i18n.cjs
```

The test uses a French browser locale to verify that first-time visitors still
see English. It checks every text/attribute binding against each dictionary,
all eight FAQs using Enter/Space, internal anchor clearance, persistence,
English/RTL restoration, clipping and overflow at 320, 375, 390, 768, 1024 and
1440 pixels. It also checks scroll and open UI state, actual video playback
through a switch, secure Shopify popup URLs, Arabic/German/English scoped axe
accessibility checks, missing dictionaries, invalid preferences and blocked
storage. Storefront popups are intercepted; no purchase is made. Screenshots
and `results.json` are written outside the repository. WebKit is Safari-engine
coverage, not a test on physical iOS/Safari or a screen-reader certification.

No deployment, merge or push is authorized by this implementation.

## Verification results — 28 October 2026

The complete audit passed in installed Chrome and Playwright WebKit 27.2:
7 languages × 6 viewports × 2 engines = 84 language/layout combinations.
All dictionary text/attribute bindings matched, all eight FAQs remained usable
with the keyboard, and no horizontal overflow or text clipping was detected.
Preference reload, RTL/LTR restoration, actual video playback through a switch,
secure purchase links, scroll/FAQ/menu state, and missing-catalog/blocked-storage/
invalid-preference fallbacks passed. Neither engine reported console or
JavaScript errors. Scoped axe scans for the header, FAQ and footer in Arabic,
German and English found no WCAG A/AA violations. Representative desktop,
tablet and mobile screenshots were visually reviewed.

CSS and JavaScript validation passed. HTML validation reports only the existing
lowercase-doctype convention. These results do not certify translation accuracy,
all assistive-technology behavior, or physical-device browser compatibility.
